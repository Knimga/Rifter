# Rifter

Turn-based dungeon crawler. App is `client/` (Vite + React 19 + Tailwind + TypeScript); `server/` is an unused stub. Run commands from `client/` unless noted (`npm run dev` at the repo root starts both).

## `handoff/` (external designers' examples)
A drop-off spot for mockups and example 3D models from external designers. The user places files there and asks you to look at them; never edit, watch or tidy the folder (the user clears it once an example is implemented, so don't link to it from code or docs).
- The designers don't know the app or its code: their files may have placeholder content, inaccurate example data (names, stats, numbers) and patterns we don't use (their own vector helpers, mesh classes, renderers, seeds).
- **UI mockups are implemented exactly as they appear**, except for the data they display: replicate their styling, layout, fonts, spacing, colors and theme, built with our components and code (palette variables, existing pieces where they match). Only the shown data (names, stats, numbers, items) comes from the game instead of the mockup.
- **3D model examples** are merged gracefully into our implementation: take their look and intent, and build them with the forge's toolkit and rules. Map their helpers onto ours (`docs/forge/05-cookbook.md`); add a shared helper only when ours lack one.
- Never copy placeholder data into the game: use the game's real data, and ask when an example disagrees with it.
- Say what you changed from the example and why (e.g. a glow below 0.5 so it stays see-through in game).

## Code sweeps
When asked to "do a sweep of the code", "audit the code" or anything like it, do a full review of the whole project (not just recent changes). Sweeps come after long implementation sessions, when issues may have piled up silently; the goal is long-term sustainability and efficiency **while keeping the game's behavior exactly as delivered** (no feature, balance or look changes; a fix that would change what the player sees or gets is reported, not made).
- **Opus only.** Sweeps are done by an Opus model. If you are not Opus, say so and stop; ask the user to switch models instead of starting.
- **Comprehensive, not sampled.** Read every source file, not only the recently changed ones, for redundancies and duplicated logic, bugs, relics (dead code, stale comments, leftover names or files), anti-patterns, and bloat.
- **End-to-end reviews (by reading, no live testing).** Trace whole workflows through every layer they touch (data → hooks → screens/components → view), for example: a new run from menu through character select into the first dungeon; movement, exploration and fog; a full combat round (turn order, abilities, areas, hits, buffs/dots/hots, enemy AI, death, xp and loot); inventory, equipping, containers, vendor, shards and the enchanter; rifts and keys; dialogue and quests; the Sanctum and its NPCs; screen transitions. Follow references across modules (ids, `model:` links, data lookups, keys) to check each resolves and stays consistent.
- **Hunt bugs and loopholes**, not just style: state that can desync or go stale, edge cases (empty party slot, large creatures, zero/negative values, full inventory, off-map tiles), order-of-operations errors, exploits a player could use (duplicating items or gold, infinite resources, skipping costs or turns, stacking effects that should not stack), and rules enforced in one path but not another.
- **Flag structural change when it is due.** Report when the code has outgrown its shape: a file or hook doing too many jobs, a folder that should split, a new module that should exist, logic that belongs on the backend (`server/`, e.g. persistence, authority over loot or progression), or a system repeatedly patched where a redesign would serve better. Propose these; do not do them in the sweep.
- Fix what is clearly wrong, and report what is a judgment call. The report groups findings by fixed / needs a decision / structural recommendation, each with file and line.
- Run `npm run lint` (ESLint: chiefly React's hook rules) and `npx tsc -b`, and fix what they report.
- Also run `npx eslint . --no-inline-config` once to see what the `eslint-disable` comments hide, and check each is still deliberate (a stable ref, a value tracked through a computed key) rather than a stale value.
- Check the docs against the code: `CLAUDE.md` and `docs/forge/` (README, contract, style guide, cookbook). Fix instructions that are outdated (renamed files, functions or options, changed rules, wrong numbers), add helpers the cookbook's toolkit is missing, and drop ones that are gone. Look through the designs for vertex math or shapes repeated across files that should become a shared helper (core or a family `_x.ts`), and report them.
- Finish with `npm run build` and `npm run forge:lint -- --drafts`.

## Procedural models (forge, `client/src/forge`)
Every model is procedural and seed-based: `(design, seed)`, no hand-authored meshes, no params, no versions. Overview, layout, workflow and linking: `docs/forge/README.md`. Read `docs/forge/03-design-contract.md`, `docs/forge/04-style-guide.md` (art direction: saturated glows on dark, serving the dungeon's atmosphere) and `docs/forge/05-cookbook.md` (toolkit, construction patterns, pitfalls, how to check) before writing a design. The details live there; these are the rules to hold to:

**Keep those docs current.** They are how a fresh context learns the forge. When a change adds, renames or removes a core or family helper, a fit or design option, a rule, or a lesson learned the hard way (a pitfall), update the contract, style guide or cookbook in the same change. Art direction the user settles (a palette, a do or don't) goes into the style guide.

- **One design per game data entry, named exactly like it** (`source`, `label`, file slug, category folder; contract "One design per data entry"). Never one design for several entries; share shape code through family helpers. `forge:lint` enforces it.
- **Requested changes and new designs go to `client/src/forge/drafts/<stem>.ts`. Never edit `client/src/forge/designs/` directly**; the user approves in `/dev/forge`, which files the draft into its category's folder.
- **Creatures: data first, size known.** Before designing any enemy, boss or summon, read its data entry (the user writes it first) for whether it is `large` (2×2 tiles). With no entry, or its size unclear, ask before starting.
- **Done means linted:** always run `npm run forge:lint -- --drafts` first. For a new model or an impactful change, also make your own `forge:sheet` screenshots, LOOK at the PNG and fix what you see; small targeted changes (a color, a length, a slight turn) skip the screenshots (README Workflow).
- **Linking:** every enemy class, summon, item base, class, interactive object, decorative object, loot and NPC has a required `model: '<design id>'` on its own data entry, added together with its new design (README "Linking"). A new map object (decor, NPC, interactive object) is placed on a map only once its design is approved; until then, propose where it goes (a soft rule).
- Draw randomness with `c.rf/ri/pick/chance`; a look the user wants fixed is written into the design. Lean long parts outward, never toward or away from the camera (style guide "Camera"). No rarity/element glow in designs, and loot never animates.
- Rifts, terrain and scenery are covered by the contract ("Rifts & Keys", "Terrain", "Dungeon scenery"). A new dungeon needs only a `riftColor` and a `terrain` style. Obstacles are game state (`ZoneData.sight`, never `floors`, is what line of sight uses); clutter is the view's only.
- Game logic must not import three.js or read geometry. Facing and motion are view state (`viewEngine/three/mapRenderer.ts`).
- **View:** isometric, one setting (`GAME_CAMERA` in `client/src/viewEngine/camera.ts`). `viewEngine/` is the whole display's view; game logic never depends on it, and it never imports game data. Never hard-code an angle or a screen offset: derive it from the camera (README "Units, orientation, camera"). Maps are `Board`s (`components/mapParts.tsx`): flat DOM floor under one CSS transform, upright DOM placed with `board.toScreen`.
