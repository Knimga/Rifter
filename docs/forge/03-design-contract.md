# Design contract

## One design per data entry
Every design is the model for exactly **one** entry in the game data, and is named exactly like it:
- `source` names the entry: `{ table: 'enemies', key: 'skeleton' }`, `{ table: 'summons', key: 'void-wisp' }` (category `summon`: creatures the party summons, forge section "Summons"), `{ table: 'weapons', key: 'plain/1h Swords' }`, `{ table: 'armor', key: 'apprentice/helm' }`, `{ table: 'offhands', key: 'buckler' }` (category `offhand`: shields, quivers and foci) or `{ table: 'npcs', key: 'denisel' }` (category `npc`, forge section "NPCs").
- `label` is exactly the entry's display name ("Skeleton", "Plain Gladius").
- The file is that name slugged: `skeleton.ts`, `plain-gladius.ts`, `plain-bastard-sword.ts`; the id is `${category}.${slug}`.
- Approved, it lives in its category's folder under `designs/`: `designs/creatures/skeleton.ts`, `designs/weapons/plain-gladius.ts` (`CATEGORY_FOLDER` in `core/folders.ts`: creatures, summons, classes, weapons, armor, offhands, jewelry, interactive, decor, loot, rifts, npcs). Shared helpers (`_sword.ts`) stay in `designs/` itself. Drafts stay flat in `drafts/`; approving one files it into its folder and fixes its imports (`approvedSource`).

`npm run forge:lint` fails if any of this drifts, if two designs claim the same entry, or if a `model` link in the game data points at a design that doesn't exist or is for a different entry (rules in `client/src/forge/dataRefs.ts`).

**The one exception: starting gear.** The Worn series (`STARTER_WEAPON_SERIES`, `STARTER_ARMOR_SERIES`, `STARTER_SHIELDS`) never drops and has no designs of its own: each Worn item borrows the design of the item it is a worn version of ("Worn Gladius" is drawn with `weapon.plain-gladius`). The lint checks every borrowed link is a model some real entry uses. Shapes shared by a family live in helper files (`designs/_sword.ts`, `_axe.ts`, `_staff.ts`); an entry's design file just calls them, e.g. `export default swordDesign('plain', '1h Swords')`, and takes its name and id from the data.

## The design object
A design is one file in `client/src/forge/designs/<category folder>/` (or `client/src/forge/drafts/`) with a default export:

```ts
const design: Design = {
  id: 'creature.skeleton',       // `${category}.${fileStem}`, lint enforces
  source: { table: 'enemies', key: 'skeleton' },   // the one data entry this is the model for
  category: 'creature',          // creature | summon | character | weapon | armor | offhand | jewelry | interactive | decor | loot | rift | npc
  label: 'Skeleton',             // the entry's display name exactly
  fit: { kind: 'standing', height: 1.12, maxRadius: 0.54 },   // or { kind: 'item', size: 0.8 }, or { kind: 'placed', height } (dungeon scenery)
  budget: 900,                   // max triangles
  build(c) { /* draw into c.mesh */ return 'Frost-Eyed Skeleton'; },
};
export default design;
```

## Seeds and variety
A design draws everything random from the seed: `c.rf(a, b)` (float), `c.ri(a, b)` (int), `c.pick(options)`, `c.chance(p)`. There are no parameters: a look the user wants fixed is simply written into the design.
- **Items** (weapons, armor, offhands: `fit.kind: 'item'`) have **one look**: every item of a name is built with `ITEM_SEED` (`core/link.ts`), so the seed only shapes that one look. Don't add choices to an item; draw the design the user asked for.
- **Creatures and characters** vary per instance: each game instance seeds from its own id (`instanceSeed`), so a design can roll variety (the zombie's clothes, a skeleton's eye glow) within its locked identity (see the style guide).

## Building geometry
`core/primitives.ts`: `loft` (rings -> limbs, blades, hafts), `frustum`, `box` (with corner jitter), `blob` (jittered low-poly ellipsoid), `bipyr` (crystal). `c.mesh.tri/quad` for custom triangles. Winding is automatic: each triangle is oriented away from the center of its convex piece, so keep pieces roughly convex. Per-face color can be a function `(centroid, normal) => RGB` (stripes, moss on top faces). Face options: `e` emissive 0..1 (>= .5 renders unlit glow), `a` alpha, `j` brightness jitter (faceting).

**Halos:** `m.halo(p, r, color)` puts a soft glow around a light the model carries (an eye, an antler tip, a spore sac): a round, additive glow facing the camera, fading from its center out to radius `r`, hidden by whatever is in front of it. It moves with the current part. Usually over an emissive face. `xf` doesn't move it, so give it its final position. Halos are the model's own lights: never rarity or element glow. `m.flare(p, w, h, color)` is a halo stretched on screen (`Halo.s`): an oval `w` wide and `h` tall, upright on screen whatever way the model faces (streaks of light: the Mote of Light's diffraction spikes).

## Parts, pivots, anchors (for animation and attachment)
`m.part('arm_l', pivot)` tags all following faces. Naming: `torso`, `head`, `arm_l/arm_r`, `leg_l/leg_r` etc. `m.anchor('hand_l', point)` for attach points. **Standing designs mark `m.anchor('feet', point)` at the middle of the stance**: `finalize` puts that point at the tile center (the bounding-box center is only the fallback, and a weapon held out to one side would pull it off the body). `finalize` adds `overhead` (standing) or `center` (item); weapons add `grip` and `tip`. Anchors and pivots are transformed with the mesh.

## Large creatures
A creature whose entry sets `large: true` (`CreatureClassData`, `data/units/enemies.ts`) fills 2×2 tiles in game: the map draws it at the center of its square (where its 4 tiles meet), so `feet` is the middle of its stance as for anyone. Build it at its true size for 2 tiles: `fit.maxRadius` about 1 (its reach from the feet), a `fit.height` to match. Its overhead anchor carries its HP bar over the square's center. The builder and `forge:sheet` show it on its 2×2 square (`designTiles`, read from the entry). Whether a creature is large is the entry's, decided before the design starts (README Workflow); how to build one is the style guide's "Large creatures".

## Rings & Amulets (category `jewelry`, forge section "Rings & Amulets")
One design per ring or amulet type (`RINGS`, `AMULETS` in `data/gear/jewelry.ts`, `source: { table: 'jewelry', key: '<type id>' }`). Identity from `jewelryEntry` in `designs/_ring.ts`. They are items (`fit.kind: 'item'`, `ITEM_SEED`, built facing +z: their outline in the x-y plane, as the icon shows it) and are never drawn on the character. On the floor they are small (`fit.size` about 0.3: the loot glow shows where they lie); in a slot their icon is zoomed in a little (`JEWELRY_ICON_CAMERA`, picked by `iconCameraFor` for every `jewelry.` design), so a piece fills its slot. A ring marks its `top` anchor where its gem or other detail sits (the plain band: the crown of its dome at +y); its icon turns it so that point is at the upper right and tips it toward the viewer across the line from its top to its bottom, so a band shows its depth (`IconCamera.top`, `poseIcon`). An amulet marks no `top`: its icon looks straight at its stone. A type's `model` is `''` until its design exists: lint skips it, and it doesn't drop; set its `model` with its design and it starts dropping (and stocking the vendor).

## Class characters (category `character`, forge section "Classes")
One design per class (`source: { table: 'classes', key }`), built on `designs/_character.ts` (`buildBody` + the class's own clothing), at `CHARACTER_HEIGHT` (the skeleton's height). Bodies hold no gear themselves: they mark `hand_r` (right fist, main hand) and `forearm_l` (left forearm, shield strap), and `src/forge/equip.ts` places the equipped weapon and offhand there (`holdGear`) from their own linked designs. Held sizes are fractions of `CHARACTER_HEIGHT` (`HELD_LENGTH`, `HELD_SHIELD_HEIGHT`). Quivers are worn on the back instead: every body marks `quiver_bottom` and `quiver_top` (`QUIVER_ON_BACK`), a quiver design is built in body units at that spot and marks the same two anchors, and equip lines them up (at its built size). An offhand held dangling (a focus) marks `dangle_grip` (where it is held) and `dangle_tip`: it hangs straight down from the left fist (`fist_l`, every body marks it), `HELD_DANGLE_LENGTH` long.

**Holds:** the arm pose follows the equipped weapon type, not the class (`Hold` / `HOLD_FOR` in `_character.ts`): one-hand (Knight/Rogue), staff (Arcanist), shoulder carry (Barbarian), bow (Archer), crossbow. A class design reads the hold with `classHold(c, key)` (the build input `c.hold`, else its starting weapon's hold) and passes it to `buildBody`; the game and `buildPreview` (equip.ts) build with the equipped weapon's hold. Holds are shared code, not designs: the forge shows each class as one row per hold its proficiencies allow (a cell per weapon type), and a hold is approved in chat. `forge:sheet --weapon "<type>"` renders a class holding any weapon type.

## Moving parts
Models are static, except parts a design lists in `motion` (`PartSpin`): each spins about an axis through its part's pivot, forever, while it is on screen (view state, like facing; the game and the forge both animate it). `frame` lets an oval part be built round and squashed, so its pattern turns while the outline stays put (the Rift's swirl). Only when the request asks for it (style guide: no animation unless asked): something on the map that is magic or alive, never loot.

## Animations
A design can list one-time `animations` (`PartAnimation`): each has a `name` ('open'), a length in `ms`, and `turns`: parts that turn `angleDeg` about an axis through their pivot (`m.part(name, pivot)`), eased, then hold the end pose. Everything that should move together goes in the animated part (a chest's lid carries its straps and hasp; the padlock stays on the body). The game plays an animation when an object's state calls for it (`MapUnit.played` / `MapObject.played`, e.g. `['open']` for a looted chest): one newly listed plays, one already listed when the object appears shows its end pose. In `/dev/forge`, a radio row (Model, then each animation) plays one on a loop in every cell; `forge:sheet --anim <name>` draws its end pose. The math is shared (`core/animate.ts`; three.js poses it in `animateParts`). Like `motion`, animations are never for loot.

An animation's steps, each naming a part (all over its `ms`):
- `turns`: the part turns `angleDeg` about an axis through its pivot (eased in and out). A chest's lid.
- `grows`: the part scales up from nothing to its full size about its pivot (`ease`: 'out', the default, fast then settling; 'in'; or 'inOut'), or with `shrink` down to nothing ('in' by default: collapsing). The active Rifter's rift opening out from its center (`activate`, `reopen`) and collapsing (`close`).
- `fades`: the part's glow fades: each face with a start color (`FaceOpts.from`) goes from it to its own color, each halo with one (`m.halo(p, r, color, tint, from)`) from it to its own. Faces and halos without one don't change. The active Rifter's lights waking from their dormant glow.

An animation that hasn't been played changes nothing (the model as built): only played ones pose the model, each at its progress. So one waiting its turn (the Rifter's `reopen`, which starts from no rift) never holds its start pose over the others. An object's model can change while it keeps its id (the dormant Rifter swapped for the active one): an animation newly called for in the same update plays from its start, so the swap shows the new model waking.

## NPCs (category `npc`, forge section "NPCs")
The people the party meets (`NPCS` in `data/world/npcs.ts`, `source: { table: 'npcs', key }`; a map places them by id, `SANCTUM.npcs`). Each is one named person, a standing design (`fit.kind: 'standing'`, about `CHARACTER_HEIGHT` tall) built facing +z, with its `feet` anchor: it stands on its tile facing its own way and never moves, but turns to face the leader who speaks to it (`MapObject.aim`), then back. It is seeded from its id, so it always looks the same: draw its look as fixed constants rather than seeded variety. One that holds a weapon names it on its entry (`holds: { link, weaponType }`, Rix's plain mace): it is drawn as a class is (`buildCharacter`, the game's map and the forge alike), its body built for that weapon's hold (read `c.hold`, as a class's `classHold`) and the weapon's own model placed in its hand; never draw the weapon into the NPC's design. Its portrait (its dialogue's, as the party's in the HUD) frames its head from the `head_top` anchor, which the class body (`buildBody`) and the golems' (`golemBody`) mark just over the head: a body built another way marks it too, or a staff or a hump rising above the head throws the framing off.

## Interactive objects (category `interactive`, forge section "Interactive Objects")
Interactable things on the map that aren't units or loot: doors, chests, the Rifter, later craftbenches. Their data entries are `INTERACTIVE_OBJECTS` in `data/world/interactiveObjects.ts` (`source: { table: 'interactiveObjects', key }`; identity from `interactiveEntry` in `designs/_interactive.ts`). They stand on a tile (`fit.kind: 'standing'`), built facing +z; on the map they face their open side (`facingOpenSide`: a door in a wall faces the floor it opens onto). Maps choose which objects they place by id (`DungeonConfig.doorObject`; containers per zone: `ZoneConfig.containers`, `BossZoneConfig.containers`). Variants share a family helper, one entry and design each (the treasure chests: `designs/_chest.ts`). Rifts are not interactive objects: see Rifts & Keys.

**Containers** (the Worn and Solid Treasure Chests, the Dead Adventurer) are interactive objects whose loot is `CONTAINER_LOOT` in `data/gear/containers.ts`, by the same id. Map generation stands each against a room's wall, its back to it, facing into the room (`placeContainers` in `data/world/gen/containers.ts`), so build one facing +z with its back at -z. An emptied one is asked to play `open` (a chest's lid swinging up); a container without that animation (the Dead Adventurer) simply looks the same emptied.

**States and composed objects.** An object that changes look with its state has an entry and design per state, sharing a family helper that takes the state as a code argument (not a design param): the Rifter is `rifter` (dormant) and `rifter-active` (`designs/_rifter.ts`). A state that holds other models builds them in from their own designs with `embed` (`core/embed.ts`), so each shape lives in one place: the active Rifter embeds the Keystone in its socket and the Rift between its struts (both tinted, so it is a tinted model too, drawn in the opened dungeon's color), takes over the rift's `motion`, and wakes with its `activate` animation (1.5 s: its lights fade up from the dormant ones while the rift grows). `embed` builds and finalizes the inner design on its own (its true size; pass `1 / fitScale(outerMesh, fit)` so the outer fit doesn't rescale it) and keeps its part names (they must not clash with the outer design's). Both Rifter states mark anchors where the keystone and rift go (`socket`, `socket_up`, `rift`). A multi-tile object is built in tile units along x, its `feet` anchor at the middle tile's center (the Rifter: 3 tiles, `maxRadius` about 1.5).

## Decorative objects (category `decor`, forge section "Decorative Objects")
Static things that fill tiles on the map: furniture, shelves, crates, statues. Nobody walks onto or through them, nobody uses them, and they never move or animate (no `motion`, no `animations`). Their data entries are `DECOR_OBJECTS` in `data/world/decorObjects.ts` (`source: { table: 'decorObjects', key }`; identity from `decorEntry` in `designs/_decor.ts`). A map places them by id, each on its middle tile facing its own way (`SANCTUM.decor`: `{ id, pos, facing, seed? }`; `seed` is the look picked in the forge, else it is seeded from its place). They stand on a tile (`fit.kind: 'standing'`), built facing +z (their front). One spanning several tiles side by side (`span` on its entry, default 1; its tiles are `spanTiles`) is built like the Rifter: in tile units along x, its `feet` anchor at the middle tile's center. With an even span the placed tile is the one right of the middle, so its other tiles run to the model's left (+x): a 2-tile object stands on x = 0 and x = 1 (the Merchant's Cart). Build it at its true size (a `fit.maxRadius` equal to its reach from the feet, a `fit.height` that never binds). Gear shown on one is never redrawn: `embed` the item's own design at the size a character holds it (`HELD_LENGTH` × `CHARACTER_HEIGHT`, measured along its length with `extentAlong`), as the Weapon Rack does with its swords, axes and bows. Things the party can use are interactive objects instead.

### Dungeon scenery (decorative objects a dungeon places)
A decorative object with a `placement` on its entry is placed by the dungeon itself, in three kinds:
- **`wall`** (wall clutter: cobwebs, torches, scratches): against a *full* wall, north or east of a floor tile (never on a
  cut-down stub, a door, the rift or a container); the tile stays walkable. Purely visual.
- **`ground`** (ground clutter: bones, rubble, mushrooms): lying on a floor tile; never blocks movement or sight. Purely visual.
- **`obstacle`**: fills `span` x `depth` tiles, standing free in a room (a tile's gap from walls, doors and other
  obstacles, never cutting a way off, never in a corridor or a room with islands); blocks movement, and sight if
  `blocksSight` (`ZoneData.sight`: the tiles sight passes over, used by every line-of-sight rule).

Which ones, and how many: `DungeonConfig.clutter` (`wall`, `ground`: objects and a density) and `ZoneConfig.obstacles` /
`BossZoneConfig.obstacles` (objects, `roomChance`, `density`). Obstacles are game state, placed by generation
(`placeObstacles`, their tiles leaving the floor); clutter is the view's, strewn at draw time (`forge/terrain/clutter.ts`,
seeded by the zone, `components/zoneScenery.ts`), never in the game's state. Clutter shares a few looks per design
(`MapObject.look`, `CLUTTER_LOOKS`), so a seed varies the look as for creatures.
- **Built in place** (`fit: { kind: 'placed', height }`): at true size in tiles, never scaled or moved. Its tile's center
  at x = z = 0, the floor at y = 0. Wall clutter stands against the wall plane **z = -0.5** (the tile's back edge), facing
  +z, within the low wall's 1.5 tiles (one made for the Sanctum, within its high walls: `WALL_HEIGHTS`); it may lie on
  the wall itself (stains, scratches a hair off it), and with a `span` reach that many tiles along it (a large Faded Wall
  Sigil: 3). An obstacle fills
  its footprint centered on the origin, `span` along x, `depth` along z (its front toward +z). `forge:lint` checks it
  stays on its footprint and on the floor (a hair into the floor, or into the wall, is allowed).
- **Flat on the floor:** a map object no taller than 0.03 tiles (a carving like the Large Arcane Seal: `FLAT_HEIGHT` in
  `mapRenderer.ts`) is drawn with the floor, under the map's tile highlights and move line, and over the floor's own
  relief (raised stones never bury it). Anything taller stands over the highlights, as models do.
- **Blank until approved:** a new entry's `model` stays `''` until its design is approved (as jewelry): it is never placed
  (a draft obstacle can't block the way unseen), and starts appearing once its `model` is set. The forge's Maps
  view places drafts too (its **Drafts** toggle).

## Loot (category `loot`, forge section "Loot")
Things lying on the floor that the party picks up but that aren't items (they never go in the inventory): the gold enemies drop, and affix shards (below). Their data entries are `LOOT` in `data/gear/loot.ts` (`source: { table: 'loot', key }`; identity from `lootEntry` in `designs/_loot.ts`). Each lies on its tile (`fit.kind: 'standing'`, built at its true size) and never moves; it is seeded by the pile it draws (`gold-<zone>-<tile>`), so each pile looks its own (the Gold Coins' scatter). Keep it low and spread toward the tile's edges: an item dropped on the same tile lies over it. No rarity glow, and no `motion` or `animations` (loot never animates). In a slot (a chest's gold, `GoldCell`) its icon is the same model seen from above at an angle (`LOOT_ICON_CAMERA`, chosen by `iconCameraFor` for every `loot.` design, in the game and the forge's icon view alike), built with `ITEM_SEED`.

**The Affix Shard** (`affix-shard`) is the one loot design that is a **tinted model** (see Rifts & Keys): a single shard shape for every affix shard (`data/gear/shards.ts`), painted when drawn in its category's `tint` (`SHARD_CATEGORIES`, muted: Attributes and Healing are both green, a mossy and a sea one). A small four-pointed, caltrop-like shard (thick, curved prongs, two rising and two dropping so it reads as an X from above), about 80 triangles, because the party window's Shards tab draws one beside every shard (`ShardsTab`; the icon is rendered once per color and cached). No halo, none in its icon. It is seeded by nothing (one look). Its forge color menu lists each shard category beside the dungeons (`forge/tintChoices.ts`; `forge:sheet --tint shard-offense`).

**Affix Shards** (`affix-shards`) are shards lying on the floor (an enemy's drop: `SHARD_DROP_CHANCE` in `data/gear/shards.ts`, held in `ZoneData.droppedShards`) and their icon in a container's slot (`ShardsCell`): one static model for every drop, whatever shards it holds. It embeds the Affix Shard several times, small, each painted for good in a category's color with `paintTint` (`core/tint.ts`), so it is not a tinted model and the shard's shape lives in one place.

## Rifts & Keys (category `rift`, forge section "Rifts & Keys")
Two **tinted models**: the Rift and the Keystone (`data/world/rifts.ts`, `source: { table: 'rifts', key }`). Every rift has the same shape and so does every keystone; a rift is painted in the color of where it leads. Each dungeon has one color (`DungeonConfig.riftColor`) that paints the Sanctum's rift into it and its keystone; every rift back to the Sanctum (where the party arrives in a dungeon, and past its boss: that one opens only when the boss falls, playing its `open` animation) is `SANCTUM_RIFT_COLOR` (`[40, 65, 175]`, a deep royal blue). A new dungeon needs only its color: no designs or files. The opening's arrival portals are the same Rift, in `ARRIVAL_PORTAL_COLOR`, playing its `open` and `close` animations.
- A tinted design marks what takes the tint with a `Tone` (`[bright, deep]`: how much of the tint and of its deep shade, `tintDeep` in `core/tint.ts`): faces with `FaceOpts.tint` (one Tone, or one per corner to blend like `vc`), halos with `m.halo(p, r, color, tone)`, a floor pool with `floorGlow(..., segments, tone)`. The Tone is added to the face's own color (usually black; the rift's void keeps its own). `TINT` = [1, 0], `TINT_DEEP` = [0, 1].
- The model never depends on the color: it builds, caches and lints like any other. The color is applied when it is drawn, `tintModel(model, color, parts?)` (`parts`: only those parts, so one model can hold two tinted things in two colors: the active Rifter's keystone and its rift, `MapObject.partTints`) (the game: `MapObject.tint` in `ModelLayer`; the forge page and `forge:sheet --tint <dungeon|#rrggbb>`). Drawn without it, its tinted parts stay black.
- In `/dev/forge` the section has a dungeon menu (every dungeon's `riftColor`, live from `dungeons.ts`) and a custom color picker that prints the `riftColor` line to paste into a new dungeon.

## Terrain (a map's floor and walls, forge section "Maps")
Not designs: one builder, `buildTerrain` (`forge/terrain/build.ts`), draws every map's 3D floor and walls from its tiles and its look (`TerrainStyle`, `forge/terrain/types.ts`): a dungeon zone's from `DungeonConfig.terrain` (a passage's `PassageConfig.terrain`, `data/world/dungeons.ts`), the Sanctum's from `SANCTUM_TERRAIN` (`data/world/sanctum.ts`). A new dungeon needs only its style, never code.
- **Style:** `floor` (`color`, `seam`, `pattern`: `'flagstones'` 1 to 4 laid stones a tile, `'cyclopean'` great fitted stones like a cyclopean wall's (laid across the tiles), `'rough'` uneven cave facets (4×4 a tile), or `'rough-fine'` the same in smaller facets (8×8); `bumpiness` 0..1, always small: units stand on it), `walls` (`color`: its top is derived from it, almost black in the same hue, never veined, and so is every wall face not facing floor or a doorway (toward deep rock, over a stub: a room corner touching its floor only diagonally); `height`: `'low'` or `'high'` full walls; `finish`: `'masonry'` coursed blocks, `'cyclopean'` huge irregular stones of many sizes fitted together (laid along the wall, not in tiles, so a stone carries on past a tile's edge), or `'rough'` bulging rock whose height varies tile to tile; `bumpiness` 0..1, a rough wall's up to about 2 for ultra-rough, craggy rock), optional `veins` (`color`, `share` of the surface, `pattern`: `'cracks'` thin winding lines or `'patches'`; `glow` lights them from within, like lava, and scatters halos over them: about a third of the floor tiles and wall faces with a vein showing get one, on one of its vein facets; `halos` sets that share). Flagstones show veins in their joints.
- **Walls:** every non-floor tile with a floor tile among its 8 neighbours. **Cutaway:** a wall with a floor tile north, east or north-east of it (between the camera and that floor: a room's south and west walls, walls between rooms, islands) is a stub, `STUB_HEIGHT` (0.2); the rest rise to their full height, `walls.height` (`WALL_HEIGHTS`: `'low'` 1.5, above the 1.4-tall doors, or `'high'` 2.25). Corners need no special case: neighbouring tiles meet and turn.
- **Doors** are openings: the door model (with its own frame) stands in the middle of the tile, jambs close its sides behind its face, and a lintel fills above it in a full wall. A doorway the camera faces opens toward the floor so the walls never hide the door: its sides splay out (the walls beside it are drawn aside, floor laid under what they uncover) and the lintel's underside rises from the door's frame more steeply than the line of sight (both derived from `GAME_CAMERA`), and rough walls barely bulge at its mouth. So a door's frame is square outside, flat-topped at 1.4 tiles (`fit.height`), about 0.92 wide and no deeper than 0.16 in front of the tile's middle (`DOOR_FRONT`), whatever its shape inside: an arched door (the Warded Stone Door) arches within a square surround, its upper corners filled with stone, or the lintel would leave gaps beside its curve.
- **Seams:** only faces bordering a lower neighbour are built, and every shape comes from world-position noise, so tiles join without seams. Seeded by the zone's id: a zone always looks the same.
- **Drawn:** the walls with the units (`MapModelRenderer.setTerrain`: they hide what stands behind them and take the fog shader); the floor on its own canvas under the map's HTML floor (`Board`'s `under` slot), so highlights, glows and the move line lie on it, fogged by the fog sheet.

## Names
`build` returns a display name (the forge shows it on hover): normally the label, or a variant name for a creature ("Frost-Eyed Skeleton").

## Changes
There are no design versions and no archive: a change replaces the design (approved in `/dev/forge`; git keeps history). How an item lies as loot (`fit.groundPitchDeg` / `groundRollDeg`, and its `fit.size`, which only shows on the floor: icons frame themselves) is presentation, not its look: change it directly in the approved design or helper, no draft. A change to a whole family (its shared helper, `designs/_x.ts`) has no draft: it applies to every design of the family at once, so show the before and after on `forge:sheet` and say it is live (git reverts it). Changing generator code changes what existing seeds look like, which is fine.
